# Hillclimb

Sustained, iterative improvement of one measurable thing against a target. You own the metric and the integrity of the experiment: supervise and review, and let subagents make the attempts. A one-off fix is a bug (call the Skill tool with "diagnosing-bugs") or a [Perf issue](perf-issue.md). This is the loop.

1. **Ground the workload.** Call the Skill tool with "how" over the target. Name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts, so a lucky early win can't end the run. "At least 50% better than baseline and at least 10 iterations" has this shape. Use the user's numbers when given; otherwise agree them with the user.
2. **Build the harness, prove it, then freeze it.** Apply the **build-the-lever** principle (call the Skill tool with "principles"). Run contrasting realistic workloads and confirm that the target case reproduces the symptom while easier cases separate as expected. If the harness cannot tell them apart, revise the workload or the metric. Before you freeze it, vet it with the checks in step 1 of [Perf issue](perf-issue.md), and make it print its error count and a count of the work done, so every keep-or-revert also shows that nothing failed and the work really ran. Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (the median of N runs, never a single run). Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change.
3. **Open the decision log.** Call the Skill tool with "show-me-your-work" and keep its one canonical log, with its columns. Log one row per attempt: `phase` is the attempt id, `decision` names the hypothesis and the change, `evidence` points to the before and after measurement files and the regression-gate run, and `result` is `kept, -12.4%` or `reverted, within noise`. Keep the raw measurements in those files, not in the row. Read the log before each attempt, and keep it out of the tree (gitignored).
4. **Ground each hypothesis** in the architecture model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), never "try memoizing something". For a perf metric, order hypotheses by the performance mantras in step 2 of [Perf issue](perf-issue.md). Borrow only their order, not that step's stop rule.
5. **Loop, one hypothesis per iteration.**
   - Hand the change to a subagent on a fast model with a tight scope. Supervise and review its diff rather than typing it yourself, per the **guard-the-context-window** principle. When several independent hypotheses are live, fan them out to parallel subagents, each in its own git worktree, per the **separate-before-serializing-shared-state** principle.
   - Measure before and after with the frozen harness, and run the regression gate.
   - Keep the change only when the metric moves past the noise and the gate stays green. Otherwise revert it in full. A tweak that "might help" is reverted.
   - Make one commit per kept fix, staging only the files you changed (`git add <files>`, never `git add -A`). Log the row either way, kept or reverted.

   Each iteration ends in a check before the next begins. If the run is unattended, call the Skill tool with "autonomous-run" and borrow only its wake mechanism, not its stop rule.
6. **Push past the first plateau.** On a stall or several rejects in a row, move to the next mantra, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number, per the **laziness-protocol** principle.
7. **Stop** when the predicate is met, or when the remaining ideas are marginal and not worth their cost. Keep the predicate as agreed; never relax it to meet it. Keep going while cheap untried hypotheses remain. If you are stuck, tell the user instead of spinning.
8. **Open the PR.** Call the Skill tool with "pr" to write the body, then open it with `gh pr create`, with the kept commits stacked in the order they landed.
