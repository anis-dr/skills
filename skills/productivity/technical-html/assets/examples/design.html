Why the folder is built, not edited

Most skills in this repo are other people's text. 139 of the 185 skill folders are copies of skills from 13 upstream repos, and those upstreams keep changing [1]. The copies cannot stay word for word, either: upstream text names one harness's tools, model ids and folders, and every skill here has to run unchanged on omp, Claude Code, Codex, Cursor and pi.

So a vendored folder is not where the text lives. Its source is four things: the upstream commit pinned in upstream/sources.json, the shared rewrites in src/rules.ts, the entry's invocation override, and the skill's own patch in upstream/patches/<name>.patch [2]. bun run skills sync combines them and writes the result over the folder [3]. Running it twice gives the same folder, and a weekly job can move every pin forward without anyone touching the text by hand [4].

The pipeline for one skill

Sync builds each vendored entry in five stages, always in the same order, inside a temporary folder. Figure 1 also shows the failure path: when the skill's patch no longer applies, sync stops at "PatchConflict" and the folder keeps its old content.

Upstream.fetchPinned fetches one commit with git fetch --depth 1 and checks it out under .upstream/<source>@<sha>. It fetches into a temporary folder and renames it at the end, so a failed fetch never looks cached, and a second skill from the same commit reuses the checkout. The pin is a full 40-character SHA because git fetches a pinned commit only by its full id [5].

Everything after the fetch happens in a scoped temporary folder that closes when the skill is written. Sync copies the entry's path there, drops a .git folder that a whole-repo path brings along, and fails with MissingUpstreamPath if the path is gone [3].

The rules then run over every .md file. Each rule is a named list of regex rewrites: skillCalls turns "Run the x skill" into a Skill tool call, issuesFolder renames Matt Pocock's .scratch/ to .issues/, and modelLines swaps hard-coded model ids for roles [6]. Sync records which rules changed some text. When every entry is done, a rule that matched nothing in any skill fails the run with DeadRules, because that rule no longer does its job [3][6].

The invocation override comes next. An entry with invocation: model deletes the disable-model-invocation: true line from SKILL.md, and deletes the matching policy lines from upstream's own agents/openai.yaml. If upstream ships no agents/openai.yaml, sync writes one with a title-cased display_name and, for a user-invoked skill, allow_implicit_invocation: false [3].

The patch goes last. Sync runs git init in the temp folder, runs git apply with the patch, and removes the .git again. Only then does SkillTree.writeFolder delete skills/<bucket>/<name> and copy the staged folder in its place [7].

Note

A hand edit in a vendored folder is lost on the next sync. Edit the folder, then run bun run skills patch <name>. The command stages the skill again without its patch, diffs your folder against that staging, and writes the difference to upstream/patches/<name>.patch. An empty difference deletes the patch file [3].

Who owns the text: the four modes

Every entry in upstream/sources.json has a mode. Sync treats each one differently, and the weekly upstream job moves only some of them [8].

The 39 ours entries are 38 skills plus one file inside the principles skill. The 25 reference entries land in two skills: 24 in principles and 1 in prototype [1].

Trade-offs and the alternatives

Most of the design sits in the order of the stages. Rules run before the patch, and bun run skills patch diffs against a staging that already has the rules, the override and the generated metadata, so a patch records only what no shared rule covers. When upstream moves, sync fails in one of two named ways: PatchConflict when a patch no longer applies, or DeadRules when a rewrite stopped matching. I prefer that to the alternatives below, which tend to fail by producing text that looks fine and is wrong.

Editing the copies in place would be simpler on day one. It turns every upstream update into a manual three-way merge across 139 folders, which the weekly job could not do alone.

Git submodules or subtrees keep upstream history, but they carry upstream text unchanged. The agent-neutral rewrites would then need a fork of each upstream, which is the cost this design avoids.

Patches alone, with no shared rules, would work for a single skill. The rewrites in src/rules.ts repeat across many skills (the pstack model lines appear in several of them), and as patches each copy would conflict separately when upstream rewords a line. A regex survives small upstream edits, and the dead-rule check catches the case where it stops matching.

Forking everything gives full control and costs a review for every upstream commit. That cost is right for the 8 skills whose text has moved far from upstream and wrong for the other 139.

The design has a real cost too. A patch conflict needs a person: edit the folder until it reads right, then run bun run skills patch <name> again. And because writeFolder replaces the folder outright, nothing protects an edit that was never saved as a patch [7].
